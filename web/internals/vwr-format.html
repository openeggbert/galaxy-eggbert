The .vwr Format

Galaxy Eggbert's binary world file: a 40-byte header, a chunk table, and palette-compressed chunks with optional sparse metadata.

Every world the game plays or edits is a .vwr file: the 78 campaign worlds and the other files in worlds3d/, every custom slot and every galaxy world. The source of truth is the code: src/GalaxyEggbert/Worlds/World.cpp (header and table), Chunk.cpp (chunk payload), BitPacking.cpp, and the record codecs. The repository's World Format.md describes the same layout with its history. This page describes the format as of 2026-11-10: header version 2, chunk version 2.

All numbers are little-endian. Offsets are in bytes.

File layout

WORLD HEADER        40 bytes          magic "VWR1"
CHUNK TABLE         chunkCount * 20   one entry per chunk, empty ones included
CHUNK DATA          variable          one "VCH1" payload per non-empty chunk

An all-air default world is therefore 40 + 1000 × 20 = 20 040 bytes.

Flag bit 0: independent saw cells

Since 2026-11-08 a saw occupies its own cell and implies nothing about the cell under it; files written since then set bit 0. Files with bit 0 clear come from the time when a saw was drawn with an invented floor. The reader keeps their data as is and reports World::hasLegacySawFloors(); WorldRuntime converts them in memory before play or editing (see World Loading), and saving the converted world sets the bit. Loading alone never rewrites a file.

Chunk table

chunkCount entries of 20 bytes. The writer emits them with X fastest, then Y, then Z; the reader uses each entry's own coordinates.

OffsetSizeFieldMeaning
08offsetAbsolute file offset of the chunk payload (0 when empty)
84sizePayload size in bytes (0 when empty)
122xChunk X
142yChunk Y
162zChunk Z
182flags0x0001 = EMPTY

A chunk is written as EMPTY only when it is all air and has no sparse metadata (Chunk::isEmpty()); an object anchored in an otherwise empty chunk keeps its chunk. A non-empty entry with size 0, or coordinates outside the grid, is a load error.

Block encoding

raw (uint16) = (type << 4) | metadata
bits 15..4   type      0..4095   (the game uses 0..440: object-m.png icons)
bits  3..0   metadata  0..15     (unused by the shipped worlds)
raw 0        Air

See Block and BlockDefinitionRegistry.

Chunk payload VCH1

Header (24 bytes, chunk version 2)

OffsetSizeFieldValue / check

164dataSizeBytespacked stream size; a multiple of 8 equal to the expected word count × 8
204extraMetaSizeBytessize of the metadata section; non-zero exactly when flag bit 0 is set

A version 1 chunk has the first 20 bytes only, no flags and no metadata. The writer always produces version 2.

Body

palette[paletteCount]           uint16 raw block values
packed[dataSizeBytes / 8]       uint64 words
metadata[extraMetaSizeBytes]    optional BMD1 section

Palette and bit packing

Each of the 1000 cells stores an index into the chunk's palette, in cell order i = x + y * 10 + z * 100 (local coordinates). Index i occupies bits [i * bits, (i + 1) * bits) of the word stream, counting from the least significant bit of word 0; an index may straddle two words. The width depends on the palette size:

Palette entries1-23-45-89-1617-3233-6465-128129-256
Bits per cell12345678
Packed bytes1282563765046327528801000

The word count is ceil(1000 × bits / 64). A chunk with four distinct blocks is 24 (header) + 8 (palette) + 256 (packed) = 288 bytes, against 2000 bytes of raw blocks. The palette is written as it is in memory; entries no longer used after editing are kept.

Sparse metadata section BMD1

SizeFieldMeaning
4magicASCII BMD1
2version1
2reservedmust be 0
4recordCountnumber of records

Then recordCount records:

SizeFieldMeaning
4localBlockIndex0-999, the anchor cell inside the chunk
2metadataTypewhat the payload is (table below)
2payloadSizeN
Npayloadtype-specific bytes

A cell holds at most one record per type. The section must contain exactly the declared bytes; trailing data is an error. Unknown types are kept and written back unchanged, which is why new types could be added without a version change.

Types 1 to 4 are present in the shipped worlds. Counted across the 81 files in worlds3d/ on 2026-11-10: 4150 objects, 398 BigDecor, 87 plate turns and 40 hint zones; no file uses types 5-8 or a non-zero block metadata nibble.

Tools

  • tools/vwr_inspect.py: read-only inspector (header fields, block counts per type and height, objects, BigDecor, hint zones). --summary gives one line per world. It decodes types 1-4 and counts the others.
  • tools/worldkit.py: the Python world builder that writes this format (used by the generators in tools/worlds/).
  • tools/GenerateSampleWorld3D.cpp: a C++ generator using the real classes.
python3 tools/vwr_inspect.py worlds3d/world999.vwr
python3 tools/vwr_inspect.py --summary worlds3d/*.vwr
Three implementations. The Python reader and writer are written by hand from the C++ code. A format change has to be made in World.cpp/Chunk.cpp, in both Python tools and, for a new record type, in its codec; then run VerifyShippedWorlds and the world tests.

Not implemented

World Format.md also sketches ideas that do not exist in the code: a header with separate X/Y/Z chunk counts for non-cubic worlds, RLE or LZ4/Zstd compression of chunks, global palettes and region files. None of these is read or written by any version of the game.

Tests

  • tests/GalaxyEggbert/Worlds/WorldTests.cpp and ChunkTests.cpp: every header field round-trips; bad magic, version, flags, chunk count, palette size, bit width and metadata framing are rejected; legacy chunk version 1 is read.
  • tests/GalaxyEggbert/*RecordTests.cpp: the record codecs.
  • VerifyShippedWorlds: every shipped world survives load → save → load.
