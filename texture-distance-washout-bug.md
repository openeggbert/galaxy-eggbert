# Texture distance washout bug (unresolved, 2026-07-10)

> **Addendum 2026-07-10 (later the same day): re-test required.** The real root cause of the
> "missing walls" family of reports was found after this document was written: `Easy3D::CubeMesh`
> wound all cube **side faces** with the OpenGL CCW-from-outside convention, while CNA implements
> genuine XNA culling (visually-clockwise triangles survive `CullCounterClockwise`) — so every
> side face was invisible from outside, and what actually rendered in its place was the mirrored
> interior of the block's *opposite* face (`../easy-3d` commit `44393f5`, `NEXT.md` §3). That
> means **everything this investigation observed on side faces was observed on the wrong face**
> (the far face's interior, one block deeper and mirrored), including this document's claim below
> that geometry/winding was "proven correct." The distance-washout symptom itself may still be a
> real, separate sampling bug — but the reproduction must be re-run on top of the winding fix
> before any of the conclusions below are trusted or the investigation resumed.

## Summary

A real, confirmed rendering bug in `GalaxyEggbertCNA`: a block face's texture renders correctly
at close range, then degrades into a flat, uniform, wrong gray color as the camera moves away from
it. This is **not** missing geometry and **not** the `+Y`/`-Y` `Easy3D::CubeMesh` winding bug fixed
the same day (see `NEXT.md` §3, `../easy-3d` commit `8ab3854`) — it is a separate, still-unsolved
texture-sampling problem.

It was first reported live as "two side walls of a cube are missing." That description turns out to
be a reasonable way to describe the symptom from a distance — a face that should show a detailed,
colorful texture instead shows a flat, featureless, near-white fill, which reads as "not really
there" at a glance — but the actual defect is texture sampling, not geometry.

## Reproduction

World: `worlds3d/world001.vwr` (generated by `tools/GenerateSampleWorld3D.cpp`), the demo row of
`kSymmetricEntries`/`kDirectionalEntries` DirectionalCube tiles starting around world X 4-6 (icon
25, one of several "unnamed variant" bulk-material demo blocks in that row).

Steps:
1. Build `GalaxyEggbertCNA` (either EasyGL or Vulkan backend — not yet confirmed whether this
   reproduces on both, unlike the winding bug which did).
2. Position the camera on a line perpendicular to one of icon 25's side faces (e.g. facing world
   +Z, looking at its `NegZ` face), at two distances along the same line: ~5 units away, and
   ~12 units away.
3. At ~5 units: the face shows its real texture (a blue background, a white horizontal stripe, dark
   vertical bars, and a small ball/rivet detail — confirmed against the source `object-m.png` crop
   for icon 25 directly, via Python/PIL pixel sampling).
4. At ~12 units: the same face renders as a flat, uniform `(211, 211, 211, 255)` gray. Confirmed by
   sampling multiple points across the rendered face in the captured screenshot — all identical,
   not a gradient or noisy pattern.
5. That exact gray value does not appear anywhere in icon 25's real source texture (checked by
   scanning the actual crop for near-`(211,211,211)` pixels — zero matches).

## What was ruled out

- **Geometry / face-culling logic**: a debug print inserted directly in
  `GEDirectionalCubeTiles.cpp`'s `kSymmetricEntries` handling confirmed the affected face has
  `Visible = true` and a UV rect that correctly maps to icon 25's real texture region in
  `object-m.png` (verified by converting the UV rect back to pixel coordinates and cross-checking
  against the known tile-atlas layout formula in `BlockTypes.hpp`'s `tileUV()`). The face's shape
  and position are correct — this is a texture-sampling problem once the face's geometry has
  already been correctly built and placed.
- **The `+Y`/`-Y` winding bug fixed earlier the same day**: unrelated. That bug made a face
  invisible outright (showing whatever was behind it) regardless of distance. This bug shows the
  *wrong color* on a face that *is* visible and correctly shaped, and is distance-dependent.
- **Classic texture-atlas mip-level bleeding**: the usual cause of "a tile packed tightly next to
  its neighbors in an atlas bleeds into a blended/averaged color at a distance" is minification via
  mipmapping without inter-tile padding. Checked `../easy-gl`'s `Texture.cpp`
  (`Texture::set_image_2d`): the atlas texture (`object-m.png`, loaded via
  `Texture2D("Content/icons/object-m.png", device)`) is created with `MinFilter = Linear` and
  `MagFilter = Linear` — plain bilinear, **not** any `*MipmapLinear`/`*MipmapNearest` variant — and
  no mip chain is generated for it (`glGenerateMipmap` is not called anywhere in this path). Under a
  non-mipmap `Linear` filter, OpenGL(ES) should always sample level 0 regardless of distance, so
  classic mip-level LOD blending should not apply here. This theory does not hold up and was not
  pursued further as the explanation, though it may still be worth re-examining if a different
  angle turns something up.
- **A `SamplerState` override at draw time re-introducing mipmapping**: also checked and disproven.
  `../cna`'s `EasyGLGraphicsBackend::ApplySamplerState` maps XNA's `TextureFilter.Linear` (value 0,
  the default) to the `default:` case of its internal switch, which — per that code's own comment
  ("Linear — bilinear, no mipmaps (CNA does not generate mipmaps by default)") — again resolves to
  plain non-mipmap `Linear`, consistent with texture-creation time. No code path was found that
  requests a mipmap-based filter for this draw call.
- **Fog**: `Microsoft::Xna::Framework::Graphics::BasicEffect::fogEnabled_` defaults to `false`
  (`include/Microsoft/Xna/Framework/Graphics/BasicEffect.hpp`), and nothing in
  `GalaxyEggbertCnaGame.cpp` ever sets `FogEnabled`/`FogColor`/`FogStart`/`FogEnd`. A fog effect
  fading toward a flat color at a fixed distance would have explained the symptom neatly, but it is
  not in play.

## Where the trail was left off

The investigation reached into `../cna`'s own EasyGL graphics backend
(`src/CNA/Internal/Backends/EasyGL/EasyGLGraphicsBackend.cpp`) without finding the actual
mechanism. Two specific, plausible-sounding theories were checked directly against that source and
both turned out to be wrong (see above) — the real cause is still open. Deliberately stopped here:
per project memory, a separate Claude Code agent is actively working in `../cna` (a sibling
directory, `cna_graphics` per earlier conversation), and editing CNA's core texture/sampler code —
which every CNA consumer depends on, not only `GalaxyEggbertCNA` — without coordinating with that
work first seemed like the wrong call. This report exists so the investigation doesn't have to be
redone from scratch later.

## Suggested next steps (not yet attempted)

- Re-run the same close/far A-B comparison on the Vulkan backend (`build-cna-vulkan`) to check
  whether this is EasyGL-specific or reproduces identically on both backends, the way the `+Y`/`-Y`
  winding bug did. That result alone would substantially narrow where to look next.
- Try disabling depth writes/reads temporarily around this draw call to rule out a depth-precision
  or Z-fighting explanation outright (a competing hypothesis that was raised but not directly
  tested).
- Check whether the "flat gray" value correlates with the *average color of the whole atlas
  texture* (a classic symptom of accidentally sampling a completely wrong/degenerate LOD or a
  fallback texture) rather than anything specific to icon 25 or its neighbors.
- Consider whether this reproduces for icon 2 (confirmed fine up close and from a wide elevated
  shot earlier in the investigation) at the *same* ~12-unit distance and angle as icon 25's failing
  case, to determine whether this is icon-specific or affects every DirectionalCube-rendered tile
  once far enough away.
